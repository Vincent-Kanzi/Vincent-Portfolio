# User Stories and Tasks

## Evidence
> ![User Stories](assets/user-stories.png)

These are user stories I wrote during my internship from the
end-user's perspective, broken into concrete tasks.

**Story:** s a house parent, I want to be alerted when an incident happens in
my residence so that I can attend to it as soon as possible.


| # | Task | Estimate |
|---|---|---|
| 1 | Create email and in-system notification   | 2 |
| 2 | Create a database that stores all repairs and incidents |4 |
| 3 | Create the application logic that adjusts and routes incidents | 3 |

## Reflection
My first attempt at user stories in coursework was really just technical tasks
in disguise "build the login API", "create the database". In my internship I
saw how expensive that mistake is at scale. A vague story caused rework in a
review. Rewriting stories in the "As a… I want… so that…" format and checking
them against INVEST made my writing materially better my later stories were
estimated more accurately and needed fewer clarification questions in stand-up.

Breaking stories into tasks was the biggest learning moment. In coursework I made
tasks far too big, so progress was invisible on the board. In the internship,
splitting work so each task fit inside a day turned the board into a genuine
progress signal. Comparing the two is the clearest evidence of my development.
